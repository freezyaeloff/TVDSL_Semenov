# HW2 — синтаксический анализатор Funny

Парсер на Python 3.10+ без сторонних библиотек: **рекурсивный спуск (ветка LL(1))**, AST в JSON, ошибки с номерами строк/колонок, восстановление после ошибок в инструкциях.

## Файлы

- `funny_parser.py` — сканирование текста через ДКА HW1, рекурсивный спуск, AST и CLI.
- `dfa.json` — таблица ДКА из HW1, которая нужна для работы лексического слоя HW2 (без кода и тестов HW1).
- `grammar.ebnf` — использованная грамматика и приоритеты операторов.
- `test_parser.py` — позитивные и негативные проверки (в том числе snapshot AST).
- `expected_basic.json` — эталонный JSON AST для простейшей функции.
- `tests.md` — автоматически создаваемый отчёт о каждом тесте.
- `demo.funny` — полноценная программа с массивами, условиями, циклом и контрактами.
- `errors.funny` — две синтаксические ошибки для демонстрации восстановления.

## Запуск

Запускать из папки `hw2`:

```bash
python funny_parser.py demo.funny
```

Вывод AST в файл:

```bash
python funny_parser.py demo.funny --out result.json
```

На Windows команда может называться `py`, на Linux/macOS — `python3`.

Проверка ошибок:

```bash
python funny_parser.py errors.funny
```

Программа выводит AST в stdout, а диагностику — в stderr в формате `строка:колонка: сообщение`. При наличии ошибок завершает работу с кодом 1. Если задан `--out`, частичное AST записывается в файл (если лексический анализ завершён).

Тесты:

```bash
python test_parser.py
```

## Архитектура

1. **Лексер** берёт 128 ASCII-переходов каждого состояния из `dfa.json`, построенного в HW1. При сканировании используется *maximal munch*: сохраняется последнее принимающее состояние. Пробелы и однострочные `//`-комментарии пропускаются. Для остальных токенов сохраняются тип, исходный текст, строка и колонка (с единицы). В конец добавляется `EOF`.
2. **Парсер** смотрит на текущий токен и выбирает функцию для функции, блока, инструкции или выражения. Приоритет выражений реализован разбором по уровням, эквивалентным LL(1)-грамматике в `grammar.ebnf`.
3. **AST** — обычные словари с `type`, `line`, `column` и полями узла. Поэтому дерево можно сериализовать в JSON и использовать в следующих работах.
4. **Обработка ошибок**: `expect()` выдаёт сообщение с позицией и ожидаемым символом. Внутри блока режим паники пропускает ошибочную инструкцию до `;` или `}` и продолжает. Если сломан заголовок/незакрыт блок, парсер может восстановиться на следующем `function`. Каждая попытка восстановления либо продвигает токен, либо выходит из текущего блока, поэтому цикл не застревает.

### Что умеет парсер

- `function name(x, y) returns (result)` и необязательное `uses (tmp)`;
- необязательные повторяющиеся `requires expr;` и `ensures expr;` (или пустые `requires;`, `ensures;`);
- присваивания, `{ ... }`, `if (...) { ... } else { ... }` и `else if`;
- `while (...) invariant expr; { ... }` (инварианты необязательные);
- `assert expr;`, `assume expr;`;
- `a[i]` и `a[i] = expr;`, вызовы `f(x)` и `length(a)` внутри выражений;
- целые числа, `true`, `false`, `not`, унарный минус, `* / + -`, сравнения, `and`, `or`.

### Сахар для массивов

`a[i] = x;` представляется **не** мутацией элемента, а присваиванием результата функционального обновления:

```text
Assign(target="a", value=ArrayUpdate(array=Name("a"), index=Name("i"), value=Name("x")))
```

Это синтаксическое преобразование в AST. Оно не выполняет копирование массива во время работы парсера: интерпретация `ArrayUpdate` относится к следующим этапам компилятора.

## Принятые допущения и отличия

**Внимание:** в предоставленных файлах есть `HW02_parsing.md`, но нет `docs/funny.ru.md` и слайдов P03/P04. Точная форма грамматики из этих материалов недоступна для сравнения. Использована явная грамматика в `grammar.ebnf`; перечисленные особенности — **выбранный подъязык**, а не утверждение об оригинальном Funny.

- Функции: `function f(x) returns (y) [uses (tmp)] ... { ... }`; имена без аннотаций типов. **Двоеточие** и другие символы отсутствуют в ДКА HW1 и не поддерживаются.
- `requires`/`ensures` отсутствуют среди ключевых слов HW1. После получения токена `IDENT` его вид переключается на `REQUIRES`/`ENSURES` при полном совпадении текста; исходный ДКА не изменён. Это не позволяет использовать данные слова как имена.
- Контракты идут **после заголовка перед `{`**, заканчиваются `;`, а `invariant` стоит **между условием цикла и `{`**.
- В качестве операторов используются токены из HW1; `=` — присваивание, `==` — сравнение. Нет строк, вещественных чисел, типов, объявлений переменных, `return`, `for` и самостоятельных вызовов функций-инструкций.
- Для левой части поддержаны `x = ...` и **один уровень** `a[i] = ...`; вложенные `a[i][j] = ...` не реализованы. В выражениях индексация может быть вложенной.
- Входной алфавит — ASCII, как в HW1. Кириллица в комментариях тоже вызовет лексическую ошибку. Файлы примеров специально используют только ASCII.
- Синтаксические ошибки внутри блоков восстанавливаются в режиме паники; при **лексической** ошибке выполнение прерывается, так как таблица ДКА не определяет токен.

## Приоритеты

От слабого к сильному:

```text
or
and
== !=
< <= > >=
+ -
* /
unary not, -
postfix: f(...), a[...]
```

Бинарные операторы левоассоциативны; префиксные унарные — правоассоциативны. Скобки меняют порядок вычисления.

## Тестирование

`test_parser.py` содержит проверки:

- **Позитивные:** объявление и контракты функции, `uses`, все базовые инструкции, циклы/инварианты, `if/else if/else`, массивы, приоритеты, унарные операции, вызовы, комментарии, несколько функций, пример `demo.funny`, сравнение AST с `expected_basic.json`.
- **Негативные:** пустой ввод, незакрытые `(`/`[`/`{`, неправильный оператор, лишние токены, пропущенное выражение, неизвестный символ, несколько ошибок подряд, восстановление до следующей функции, 300 ошибочных инструкций без зависания.
- **Интеграционные:** координаты и значения токенов, maximal munch, ключевые слова, переводы строк Windows, несовместимость с non-ASCII, сохранение поведения HW1.

Команда `python -m unittest -v test_parser` сравнивает результат с ожидаемыми значениями и падает при несовпадении. Все тесты запускаются локально, сеть не нужна.

## Состав архива

Только файлы, необходимые для HW2, и `dfa.json` как зависимость для интеграции с HW1. Исходники и тесты первой домашней работы в архив не включены.

## Структура как в hw1

Все файлы лежат в одной папке, без вложенных каталогов и пакетов:

```text
hw2/
    README.md
    funny_parser.py
    test_parser.py
    grammar.ebnf
    dfa.json
    expected_basic.json
    demo.funny
    errors.funny
    tests.md
```

Как и в hw1, основной файл поддерживает запуск проверок:

```console
python funny_parser.py --tests
```

Эта команда и `python test_parser.py` сохраняют отчёт `tests.md` рядом с кодом
и возвращают код 0 при успешной проверке, 1 при провале.
`python -m unittest -v test_parser` запускает те же тесты без обновления отчёта.
Можно совместить проверку и разбор:

```console
python funny_parser.py demo.funny --out result.json --tests
```

Проверено на Python 3.12.14: 30 тестов, включая исходные 27 проверок и
3 проверки запуска из командной строки. Проверяются JSON в консоли, запись
AST при запуске из другой папки, код 1 и частичное AST на ошибочном примере.
`dfa.json` загружается относительно `funny_parser.py`, поэтому наличие hw1
рядом не требуется. Пути входного файла и `--out` задаются относительно
текущей папки; родительская папка `--out` должна существовать.
